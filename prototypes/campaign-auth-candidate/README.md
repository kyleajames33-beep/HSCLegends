# Campaign auth and content candidate

**Isolated staging-design experiment. Not a production migration, not app-integrated, not deployed, and not proof of Supabase authorization.** This is a separate candidate based on `../campaign-authority`; it does not change that lab. Fixtures are invented, and all balances and scores are synthetic.

The candidate replaces the old public trusted-actor API with `campaign_api` wrappers that accept **no actor parameter**. Each wrapper obtains a UUID from `auth.uid()` and calls a private, owner-checking function. Only a synthetic `authenticated` role can execute the wrappers; `anon` cannot. Browser roles cannot access the private schema, question keys, session snapshots, actor-taking functions, action log, wallet or ledger. Fixed search paths, explicit revokes and private schemas are used in this lab. The APIs serialize state mutations with row locks, grade answers server-side, reject stale versions and conflicting request replays, and claim wins once.

## The authentication boundary is an assumption, not a verified deployment

This local database creates a **mock** `auth.uid()` that reads a PostgreSQL setting (`request.jwt.claim.sub`). The tests set that value directly to model requests from two identities. A direct SQL session can also set it and impersonate anyone: both test suites explicitly demonstrate this. Therefore the candidate is safe only if a trusted request gateway verifies a real token, supplies the authenticated claim, and untrusted users cannot open direct SQL sessions or invoke a claim-setting routine. The role name `authenticated` itself does not authenticate a user.

Before any staging or production use, inspect the actual Supabase/PostgREST configuration, exposed schemas, actual `auth.uid()` implementation, token validation, JWT issuer/audience/expiry, role membership and connection access. Remove the synthetic `auth` schema, mock function and synthetic roles; use existing Supabase auth primitives. Independently test real signed sessions, another user's token, forged/expired JWTs, anon, user-to-user isolation and direct-connection denial against a **separate staging project with synthetic data**. Never deploy or grant this file as written. Review `SECURITY DEFINER` ownership/search paths, all grants, schema exposure, RLS and Supabase database advisors. No existing live schema or grant is assumed.

## Reviewed-content interface

Synthetic releases have subject, syllabus, immutable revision and draft/released/revoked status. Questions carry a source ID, review status, reviewer and review time. A run starts only against a released revision and copies the **approved** questions, keys, options, explanations and review metadata into a private run snapshot. Content under a released/revoked revision cannot be edited or deleted by the lab authoring path; existing runs hold a stable question set. Draft questions are excluded; no approved questions means no run is created. Revocation prevents new runs and new actions. Identical previously recorded action retries can still return their prior receipt; already-won runs may claim their previously earned synthetic reward. This policy is a candidate, not an approved production policy.

The `reviewer` field is metadata; it cannot establish that a human actually checked scientific accuracy or syllabus alignment. There is no educator review, source provenance system, real syllabus mapping, question ordering or question-pool diversity in these fixtures. Before staging, establish reviewed identities, content source/version, approval workflow, validation rules and a policy for revoked content in already-active games. Reconcile existing HSC bank restrictions and ensure answer keys cannot leak through any other endpoint.

## Running isolated checks

- `npm ci --offline --ignore-scripts` when cached (otherwise `npm ci --ignore-scripts`), then `npm test`: in-memory PGlite checks for ownership, privileges, forged actor parameter, immutable snapshots, no approved content, action validation, idempotency, private receipts and explicit direct-SQL spoofing.
- `./test-postgres-roles.sh`: requires a local `postgres:17` image and Docker. It creates a disposable container with `--network none`, checks real PostgreSQL roles/privileges and synthetic claims, then observes lock waits across two independent connections for competing answer and duplicate claim with both commit and rollback. It tears down the container.

These tests do **not** prove real JWT verification, database access boundaries, cross-service behavior, production concurrency, browser gameplay, current schema compatibility, complete HSC coverage or correct real-user rewards. Two-connection cases test these specific interleavings only. Identity/account revocation, tokens changing during a session, hostile request rates, live migrations, game balance, score policy and real failure recovery remain open. The client-authoritative existing Campaign must not be switched to this candidate until those issues and a reviewed migration are addressed.

## Browser adapter (candidate only)

`client.ts` is a typed, unwired adapter for a transport already scoped to the candidate `campaign_api` schema. It sends only run ID, reviewed-release ID, action ID, expected version, action and answer choice where applicable. It never sends an actor, damage, energy, score or reward amount. `setContext(accountId, runId)` binds local request ownership; these IDs are local guards, not authorization. The caller must derive identity from a verified auth session and invoke `setContext` immediately on every account/run change, sign-out and disposal. A change aborts the previous request and invalidates its result, even if the transport ignores abort.

The adapter validates run, action ID, request version, receipt question, result shape and basic game-state consistency. The SQL candidate includes run/request/version provenance for actions and run/version/turn provenance for receipts. It rejects foreign, older or contradictory snapshots. After a successful mutation, refresh state before issuing the next action. If an action's outcome is uncertain because the response failed, was malformed or was lost, unrelated actions are blocked and `retryUncertain()` repeats the exact action ID, version and payload. Server-side replay must remain idempotent. The adapter keeps that pending action in memory only: reload/crash/cross-device recovery needs a designed durable request-ID store or server reconciliation; switching context intentionally discards the old local pending action. Do not claim reliable cross-device recovery from this prototype.

Consistency validation embeds this fixture's current combat constants and transitions. A production protocol must explicitly version rules and coordinate client/server upgrades; otherwise a legitimate balance change can cause a client to reject valid results. This client does not provide that version negotiation yet.

An RPC error may be a known rollback or an ambiguous transport failure; the adapter conservatively treats both as uncertain. An old replay response can be rejected after another device has moved the observed version ahead; recovery needs an explicit reconciled protocol. The caller must never infer a receipt or award from scores. Runtime abort is best-effort: it does not cancel a transaction that already committed. Returned answer keys, deadlines and currency must remain server-authoritative. No client validator can prove a response came from an honest database or replace JWT, grant and ownership checks.

`test/client.test.mjs` uses deterministic transport doubles plus one adapter-to-PGlite integration. It covers context changes, signal abortion, malformed/foreign/stale responses, inconsistent game results, caller mutation, uncertain exact retry and no actor/reward inputs. It does not test a real Supabase SDK connection, browser scheduling, process restart, durable retry, cross-device recovery or signed-token handling.
