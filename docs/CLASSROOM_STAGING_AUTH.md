# Classroom staging guest authentication

`lib/classroom-v2/guest-auth.ts` coordinates a caller-supplied **dedicated staging** Supabase browser auth client. It does not enable Supabase Auth, create the SDK client, configure credentials, provision a project or change database permissions. It rejects remote HTTP and the known shared production hostname, including a trailing dot. Its staging marker and URL check cannot prove that any other endpoint is disposable: explicitly configure a separate isolated project and separate SDK storage key before use. The known shared project must not be used for anonymous auth.

Start the controller and subscribe to its immutable snapshots. A `ready` actor has been read from `getUser`; only the server's verified identity and ownership checks can authorize classroom operations. Every auth event (except the initial event already covered by `getUser`) immediately clears the actor and increments a generation before scheduling a fresh lookup. Dispose the classroom client and room polling on each generation change. The callback does not await auth SDK work. `retry()` handles a failed or timed-out lookup. A service error is `unavailable`, not a signed-out invitation.

Anonymous sign-in requires an explicit action after a verified missing session; existing identities are never intentionally replaced. Duplicate attempts are rejected, and CAPTCHA tokens can be passed through when configured. Creating an anonymous user is a real request: closing a screen or disposing the controller cannot cancel an already sent sign-in. Prevent account switching while it is pending and keep the SDK isolated from the main application's auth storage. The result `requested` means the sign-in request completed; observe the later `ready` snapshot for a verified actor. `dispose()` unsubscribes and invalidates local callbacks, but does not sign out or delete an account.

Guest authentication must be separately enabled and protected from abuse in an isolated staging project. Anonymous Supabase users use the `authenticated` database role; existing policies, RPCs and grants must therefore be reviewed before enabling the provider. Anonymous users cannot recover a lost session on another browser or device just from a room code, alias or selector. The SDK handles its own session persistence; the controller never stores tokens. Guest expiration, account cleanup, linking, rate limits, real JWT behavior and cross-device recovery remain open. See [Supabase anonymous sign-ins](https://supabase.com/docs/guides/auth/auth-anonymous) and [auth events](https://supabase.com/docs/reference/javascript/auth-onauthstatechange).

The focused tests use a fake auth adapter. `tests/integration/classroom-guest-auth.local.mjs` is an opt-in real-auth smoke test requiring `HSC_LAB_ALLOW_DISPOSABLE=1`, `HSC_LOCAL_SUPABASE_URL` and `HSC_LOCAL_SUPABASE_PUBLISHABLE_KEY`. It checks the exact labelled disposable containers, loopback-only port bindings and public key before creating an anonymous user, and verifies session recovery and sign-out. It does not clean up that auth user; delete the disposable local stack after the test. Never point it at shared staging or production.

The real-auth smoke test has not yet run. In this workspace, local Supabase startup failed when its Realtime migration attempted IPv6 on an IPv4-only Docker network. An IPv6-enabled network progressed past that migration, but the GoTrue migration could not reach the database over IPv4 even though IPv6 TCP succeeded. A final IPv6-only, loopback-published attempt left a healthy database but the CLI stalled at database startup and never launched Auth. The precise cause of that last stall is unconfirmed. The temporary containers, volume and networks from these attempts were removed; no hosted database was touched. These infrastructure observations do not establish that the auth controller works against real Supabase.
