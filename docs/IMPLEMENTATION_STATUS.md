# HSC Legends implementation status

Updated 4 November 2026. This records local work in progress, not a deployment or a claim of production readiness. The delivery plan remains in `GAME_PLATFORM_DELIVERY_PLAN.md`.

## Available now

- Game-first home and navigation; Lab Tycoon has a timer, cash, income targets, upgrades, streak feedback and an evolving lab. The connected version requires a configured Supabase project; it shows persistent Sparks only after the RPC reports success. This display change does not fix server-side award authority.
- Home and the game library now use a consistent dark arcade palette with illustrated playable cards. `/arena` is a complete Knockout Solo game: eight bounded survival rounds, simulated rivals, hearts, timed questions, Shield/Scan choices, rankings, replay and missed-answer review. It uses the existing unreviewed Chemistry sample, runs without account services and grants no wallet rewards.
- Knockout Solo selects a seeded, non-repeating question order per run and can resume in the same tab after navigation or refresh. Its session-scoped action log is validated and replayed through the game rules; an active round's original deadline continues to run. Corrupt or incompatible saves are ignored. This is local practice recovery, not an authoritative classroom receipt or cross-device save.
- `/demo` runs an account-free, self-contained Chemistry sample, including when backend settings are absent. Two starting kits trade a stronger blast for more time. Correct answers damage a reactor boss and charge a player-triggered blast or extra time; upgrades increase cash and attack power. Players can stake in-run cash on Overclock: a correct answer returns the stake and doubles its normal earnings while adding damage; a miss loses the stake. Optional sound effects start muted; a local personal best is saved when browser storage is available. Missed questions and explanations can be reviewed at the end of the run. The clock pauses for feedback and the shop. Sample content is not official or scientifically reviewed. Generate `public/lab-rush.html` from its source and sprite with `node scripts/build-lab-rush.mjs`.
- Lab Rush upgrades now have distinct income, attack and time roles. The boss exposes its core at 50 HP, increasing blast damage. Results show the kit, damage, purchases and a factual highlight with same-kit replay. `LAB_RUSH_RULES.md` and `scripts/lab-rush-balance.mjs` record the actual rules and a limited deterministic balance model.
- The shared viewport permits browser zoom. Campaign has a redesigned arena and guards for duplicate/stale actions and failed victory confirmation. Campaign remains dependent on its existing backend.
- Classroom, Knockout and Gamble rejoin paths reject a different returned player or room. These checks prevent accidental identity changes; client-saved IDs are not authorization.
- The existing classroom host can copy an invite URL containing only its six-character code. The join form accepts that validated code and prevents duplicate player creation while a join request is in flight. Synthetic transport tests cover these client behaviors; deployed multiplayer permissions and the missing server receipt remain unresolved.
- Classroom v2 and Campaign have isolated, explicitly staging-oriented server contracts and client adapters. Their synthetic lifecycle and concurrency tests exercise receipts, ownership and stale responses; neither adapter is wired into live gameplay. Tycoon and Gamble also have isolated server-authority candidates. These are development groundwork, not deployed fixes.
- The classroom v2 candidate guards host actions against stale room/version callbacks and invalidates old student bindings on entry to another room. Optional polling and same-tab recovery helpers bound stale responses and require a fresh server snapshot. The candidate can retain unreviewed teacher explanation and course/source metadata in private synthetic rows and offers owner-only readback in the isolated lab; it has no reviewed content workflow or durable archive. These components are not enabled in the live classroom and do not by themselves prove Supabase authentication.
- `/classroom-staging` is a separate, disabled-by-default test interface with host and guest sign-in, room creation, joining, polling, server receipt display and same-tab recovery. It can explicitly host a revalidated local teacher draft, and the candidate returns that draft's explanation only after the student's own receipt. Its test-only configuration rejects the known shared project and does not enable the live classroom. Focused UI tests use doubles; real Supabase authentication and browser multiplayer still require verification on a disposable stack. Local stack attempts failed during setup; see `CLASSROOM_STAGING_AUTH.md` for the observed errors and cleanup.
- Staging hosts can copy a same-origin invite link that prefills the room code. The candidate host snapshot returns the code to its authorized owner after recovery, while older snapshots retain a clearly unverified local fallback. Student snapshots from the updated candidate include a validated question total and, when complete, a server-calculated placing with tied scores sharing a place; older snapshots omit these fields. The long code is a room selector, not proof of participant identity; the separate staging server candidate has not been deployed.
- Staging join accepts either a valid code or a same-site invite link and rejects malformed input locally. A host cannot start an empty room; the candidate serializes join and start using the room lock. A joined participant is not necessarily currently connected.
- A staging host can end a lobby before the first question; participants see that it ended before play and receive no placing. Known deadline, stale-question, authorization and expired-room responses are shown distinctly without exposing arbitrary backend error text.
- If browser session storage is blocked, staging authentication falls back to a page-local session and warns that the sign-in will be lost on refresh. This does not recover an anonymous user whose session is already lost.
- After an authentication refresh, the staging page attempts to restore a room only when the same actor is reverified and a fresh server snapshot succeeds. An uncertain host-creation request is retained for a same-actor retry and not transferred to a different actor. These behaviors are covered by local doubles; real Supabase session transitions remain unverified.
- Staging teachers can choose the question duration before creating a room. Once the game is complete, an owner-bound student snapshot can include that participant's submitted-answer review; unanswered questions and other students' answers are not returned. Both features remain part of the isolated candidate and need real authenticated staging tests.
- After a staging game ends, the owning host can see and download aggregate correct/submitted counts per question; questions never opened are labelled unplayed. These figures do not treat missing submissions as incorrect and are not an individual assessment report.
- When backend configuration is missing, the public game hub and sample remain usable; connected routes explain that they are unavailable. Solo reward displays wait for a confirmed balance instead of reporting an unconfirmed award as successful.
- Account lookup distinguishes a missing session from service errors, stops waiting after a bounded timeout and ignores initial lookups made obsolete by later sign-in or sign-out events.
- The production service worker caches only the self-contained Lab Rush and a public offline landing page. After installation, losing connectivity opens offline play rather than a cached account screen. Account and classroom responses are never stored by this worker; old owned caches are removed without deleting unrelated application caches.
- Normalizer output includes a hash in its audit. Seed preflight rejects tier metadata the current schema would lose and mismatched or blocked audited imports. Legacy unmarked input is still accepted with a provenance warning. Existing SQL batches are not overwritten or deleted.
- `/question-import` validates teacher CSV/JSON locally, blocks malformed or unsupported rows, preserves the supplied course/version/source fields and exports an explicitly unreviewed draft. The draft can be played locally in Knockout Solo with simulated rivals and survives refresh in that browser tab. It does not upload or start a classroom. `seed-rest.mjs` is now dry-run by default, requires an explicit target for apply, and guards the known shared production host; it is a separate format from teacher drafts.

## Open launch blockers

1. The classroom uncached answer-receipt regression remains red. `prototypes/classroom-receipts` demonstrates a separate SQLite model with Node 24; it is not used by the app or a deployed API. Obtain an authorized schema-only baseline, choose guest authentication and implement and test the actual Supabase contract.
2. Retained Knockout/Gamble migrations expose answer or decision data and allow mutations by caller-supplied identity. `docs/KNOCKOUT_GAMBLE_SECURITY_CONTRACT.md` and `prototypes/gamble-security` explain a bounded experimental contract; neither secures production. Campaign and Tycoon rewards also require server authority. Verify actual staging functions, grants and identity before modifying or relying on them.
3. Review and map content against the actual course and syllabus version. Import checks and explanation presence do not establish correctness. Do not seed blocked source rows or market the sample as verified coverage.
4. Perform connected multiplayer and signed-in browser/device testing against disposable staging data, including reconnection, simultaneous requests, timer and reward outcomes.

**Confirmed shared-wallet issue:** read-only inspection of the deployed `credit_coins` function and its grants shows that an authenticated caller can repeatedly supply an arbitrary positive amount for their own wallet without an award receipt or idempotency check. The function is shared with other HSC Science consumers; avoid revoking it blindly until callers, server-owned replacement paths and rollout/rollback are established. No exploit call or database mutation was made during the audit.

Read-only production metadata on 3 November 2026 confirms that the game-estate lockdown migration was applied. All inspected `ko_*` and `gamble_*` RPCs, including join and submit, deny execute to both `anon` and `authenticated`. Classroom `submit_answer` likewise denies both roles; classroom create/join/start/read/rejoin permit `authenticated` only. This explains why the existing flows cannot simply be treated as usable in the connected project. These observations establish privileges, not the correctness of function bodies, ownership or a reason to remove the lockdown. The related staging project is inactive; no staging or production configuration was changed.
