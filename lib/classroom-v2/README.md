# Classroom v2 client: staging candidate only

This library is not imported by the live app. It does not enable a feature, authenticate a caller, change grants, or deploy SQL. It requires an explicit staging opt-in, an RPC transport and a successful `classroom_v2_capabilities` response. The marker is compatibility metadata, not proof that an endpoint is safe or that an identity is verified. Use a separately configured staging project; never point this candidate at production.

Call `initializeClassroomV2` with `enabled: true`, `target: 'staging'`, the authenticated actor UUID, `isCurrentOwner`, an `authGeneration` callback, and an explicitly supplied transport. The transport must forward the listed RPC names to the intended staging endpoint using its authenticated session and return `{data, error}`. Disabled or invalid configuration sends no RPC. Unsupported or inaccessible capabilities return an unavailable result; no permissions are broadened.

The generation must be a monotonically increasing safe integer, incremented on **every** authentication/session transition, including switching away and back to the same account. Dispose the client immediately on every transition and component teardown. This guard suppresses stale UI callbacks; only the server's verified `auth.uid()` authorizes actions. The local mock does not test Supabase Auth or anonymous-user recovery.

Use `prepareCreateRequest` once with a fresh UUID and preserve the entire resulting request for retries. A retry must submit the same ID, ordered questions, and duration; losing that request after an ambiguous failure requires reconciliation, not silently inventing a new ID. Freeze and validation prevent later changes to the local request; the staged server rejects a changed replay. Rebind a student's room and participant IDs after join or reconnect. Snapshots omit answer information until that participant has a receipt. Answer retries return the originally accepted choice and score rather than claiming a new choice was accepted.

The isolated `teacher-drafts.mjs` mapper can revalidate a teacher JSON draft and prepare a request including explanation and course/source provenance, explicitly marked unreviewed. The matching SQL candidate stores the metadata privately with the immutable question. The client refuses to send that metadata unless the candidate advertises `teacher_content_version: 1`; this marker does not authenticate an endpoint. The caller-supplied content revision is not verified or a stable published identity. No review workflow, data retention policy or live integration is implemented. The SQL and client must be deployed and reviewed together only in a disposable staging project.

For a confirmed host room, `teacherQuestions(roomId)` reads frozen question content and unreviewed metadata through the separate `teacher_readback_version: 1` capability. The server requires that room's enabled host and rejects expired rooms. The response contains answer keys: do not expose it in student views, share links or general caches. It is room-scoped readback, not a reviewed question bank, assessment report or durable teacher archive. Client validation and stale-response checks complement, but do not replace, server authorization.

Host controls require a successful room creation or host snapshot first. Refresh the host snapshot after transitions and bind controls to the displayed room and version; callbacks for an old room or version are rejected locally, while server checks remain authoritative.

`polling.ts` provides an optional snapshot polling primitive for a future staging UI. It backs off on failed reads, ignores superseded responses, stops automatic retries on a hung read, and bounds unresolved requests; `refresh()` explicitly retries. Dispose it on every room, actor or authentication-generation change before disposing the client. It does not issue credentials, establish identity, cancel an underlying network request, provide realtime guarantees or authorize access. It is not wired into a live route.

The separate SQL candidate is `prototypes/classroom-v2/staging-candidate.sql`, with disposable synthetic PostgreSQL tests at `prototypes/classroom-v2/test/postgres-concurrency.mjs`. Run its tests with `node prototypes/classroom-v2/test/postgres-concurrency.mjs --staging-candidate` and the adapter tests with `node --test tests/offline/classroom-v2-client.test.mjs prototypes/classroom-v2/test/promoted-client.test.mjs`. The integration test uses PGlite and a fake RPC envelope; it is not a real PostgREST or Supabase Auth test. The concurrency test uses a local `postgres:17` Docker container with `--network none`, then removes it. No real user data is used.

Before wiring even to staging, establish real Supabase anonymous-auth policy and session recovery, host enrollment and abuse limits; verify endpoint and verified JWT handling, real PostgREST shapes, concurrency, RLS and grants in a dedicated staging environment; design reconnect/realtime and account lifecycle; review migrations and operations; and approve an explicit feature gate. The old shared question bank may expose correct answers, so this design does not claim question secrecy. No legacy RPC is reopened by this code. Production integration needs a separate security and deployment review.
